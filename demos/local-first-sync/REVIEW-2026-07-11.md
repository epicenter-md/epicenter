# Historical review: server-authoritative SQLite sync

> Historical only. Do not implement from this file. The original 2026-07-11
> review is preserved in git history, where it records several discarded
> intermediate architectures. Current decisions live in ADRs 0119 through 0126;
> the executable target lives in
> `specs/20260711T103822-server-authoritative-sqlite-sync.md`.

The original review was useful archaeology, but its successive “final” sections
taught mutually incompatible systems. In particular, the following proposals
are rejected and no longer appear here as implementation guidance:

- `patchRow` plus tombstones and record-plane KV;
- authored schema epochs or revisions;
- database-incarnation migration as the target vocabulary;
- source freeze and unfreeze;
- transition or executor leases;
- server-executed application transforms;
- migration-time device or actor rosters;
- post-activation private-overlay import or generic late reconciliation;
- table routing, splits, merges, and id-changing transforms.

The surviving model is deliberately smaller:

```txt
user approves after important devices show Synced
  -> trusted client reads canonical records database A at head H
  -> client builds and validates immutable successor candidate B
  -> schema-blind authority seals the transport-complete candidate
  -> authority activates candidateId only if A is still current at H
```

Ordinary writes atomically recheck that A is current and writable before they
fold and advance its head. Migration requests contain no device-participation
state. Forgotten old local databases remain readable and exportable but never
rejoin automatically.

See `gates/GATE3-EVIDENCE.md` for the withdrawn Gate 3 status and the replacement
proof obligations. Use git history only when investigating why an older model
was rejected.
