# Cold-start architecture review: server-authoritative SQLite sync and the greenfield developer API

> Historical review. Its `patchRow`, tombstone, and record-plane KV sections
> describe discarded intermediate designs. The active contract is
> `specs/20260711T103822-server-authoritative-sqlite-sync.md`; the gate evidence
> under `demos/local-first-sync/gates/` records the implemented three-verb,
> physical-deletion, eager-root-KV architecture.

Date: 2026-07-11. Independent cold-start review of ADR-0119/0120/0121
(Proposed), `specs/20260711T103822-server-authoritative-sqlite-sync.md`
(Draft), and the `demos/local-first-sync/` research harness, worked from the
desired developer experience backward. Evidence: an API caller census across
all production apps, the Drizzle-layer git history, current-source
verification of five external sync systems, current Cloudflare Durable Object
documentation, and a type-checked disposable API prototype
(`api-prototype/api.ts`, `api-prototype/usage.ts`, `bun x tsc --noEmit` exit 0
with six enforced `@ts-expect-error` negatives).

## 1. Executive memo

### One-sentence architecture (recommended, unchanged in substance)

Each app declares its model once with `defineWorkspace`; every device holds a
complete typed SQLite replica queried locally; every product write is one
atomic mutation (`patchRow`/`deleteRow` cells) recorded in a local outbox and
ordered by a schema-blind per-`(principal, app)` server; collaborative bodies
are separate lazy Yjs documents.

**Keep the custom protocol.** Every serious external candidate fails at least
one durable promise on current evidence (§8), and the protocol core is small:
two wire operations, four server-side owners, five client-side owners.

### Strongest parts of the proposal

- The refusal set is the design. Terminal deletion, no selective rejection,
  no pending-edit discard, and no background conflict inbox are what make the
  client representation collapsible (§5): they jointly imply that a pending
  write only ever leaves the outbox by containment, which is the exact fact
  that makes a canonical shadow unnecessary.
- Server acceptance order as the only conflict clock deletes the entire
  distributed-conflict problem for metadata, and the demo's proof 6
  (acceptance order beats wall-clock LWW on a discriminating interleaving) is
  real evidence, not vibes.
- `patchRow`/`deleteRow` as the whole wire language survives every reduction
  attempt in this review (§7).

### Contradictions and defects found

1. **The gates design contradicts the ADRs and must be rewritten before Gate
   1.** `gates/DESIGN.md` and `gates/protocol.ts` still encode row
   generations with reinsert (`gen + 1`), three ops (`row-insert`, `cell`,
   `row-delete`), a mutation UUID **plus** clientSeq, a server-assigned
   clientId, and a mandatory schema-blind canonical client store with a
   derived projection. ADR-0120 refuses row reincarnation (restore = new id),
   collapses the ops to two, and the spec refuses the UUID. The spec admits
   this staleness; the rewrite is Wave 1's first task and this review's Gate
   1 handoff (§12) specifies it.
2. **ADR number 0092 is a collision.** Two accepted ADRs share it:
   `0092-identity-is-the-partition.md` (cited by ADR-0119 and the spec) and
   `0092-sign-in-migration-child-doc-guids-are-derived-from-the-schema.md`
   (cited by ADR-0121). Both links resolve, but "ADR-0092" is ambiguous
   across the three new documents; 0079 and 0101 are also duplicated numbers
   in the directory. This review disambiguates the citations in the Proposed
   docs by title and flags the renumber for the team (renumbering accepted
   ADRs is out of scope for this review).
3. **A missing migration step that would corrupt sync:** on a breaking
   (major) migration, the client must rewrite its **pending outbox
   mutations** through the same transform as its rows. The spec migrated rows
   and paused old clients but never said what happens to an outbox authored
   under the old schema; draining it is impossible (the server pauses the old
   major) and pushing it after upgrade would write old-shape cells into a
   new-major database. Added to the spec and Gate 3.
4. **Fold totality was unstated.** If synced application tables carry
   NOT NULL / CHECK / UNIQUE / FK constraints, applying an accepted mutation
   can fail locally on data another replica accepted — divergence or a
   permanent pause. The physical DDL for synced tables must be loose (PK on
   `id` only); validation lives at the write API; UNIQUE is refused as DDL
   (two offline devices can both take a "unique" value and both writes enter
   server order). This also answers spec Open Question 12: incomplete or
   newer-schema creates are storable by construction; the typed read boundary
   classifies them, the fold never fails.
5. **Per-mutation envelope is overweight.** `protocolMajor`,
   `databaseGeneration`, and `appId` repeat per mutation what the
   connection/request envelope already owns. The mutation is
   `{actorId, actorSequence, operations}`; everything else is negotiated per
   request (§6).

### Hidden second systems (named and dispelled or priced)

- The gates' canonical client store + typed projection was a second database
  on every client. Not earned (§5).
- The mutation UUID beside actor sequence was a second identity system.
  Deleted (§6).
- Per-row `_v` + migrate-on-read is a second, permanent migration system
  running inside every read. The caller census shows all 41 production tables
  are single-version — the machinery has zero multi-version producers today,
  so the greenfield replaces it with eager whole-database migration (§4).
- KV as a wire concept would be a third operation family. Already collapsed
  by ADR-0120 to a reserved row namespace; this review confirms the public
  KV API earns its keep as an ergonomic surface (42 production declarations,
  39 in Whispering) while owning zero wire or storage novelty.

### Largest unearned abstractions in the current codebase (greenfield deletions)

- `_v` stamping/stripping/routing, `TableNewerWriterError`, three-bucket
  `scan()` classification: replaced by eager migration + a diagnostic
  nonconforming lane at the read boundary.
- `bulkSet` (0 callers), `clear` (0), KV `delete`/`reset`/`getAll`/
  `getDefault` (0 production callers each), `openWorkspaceSqlite` public
  export (0 production callers).
- The whole-row LWW write model itself (`set` = whole-row replace) —
  replaced by cell-level `update` lowering to `patchRow` of named cells only.

### Asymmetric refusals this review adds

- No UNIQUE constraints and no FK enforcement in synced DDL (buys a total
  fold; costs advisory-only uniqueness).
- No per-mutation protocol/app-version stamps (buys a smaller outbox and log;
  costs nothing — the request envelope owns negotiation).
- No downgrade support: a binary older than the local database revision opens
  read-only or refuses (buys deletion of reverse migrations).
- No canonical client shadow unless Gate 1 falsifies §5 empirically.

### Unresolved product decisions (flagged, not decided here)

- Active-replica limit and actor revocation UX (spec Open Q5).
- Child-doc reclamation after parent delete (spec Open Q11) — unchanged.
- Whether `list()`-level filtered reads are enough for the first production
  apps or the SQL escape hatch becomes the primary read path in practice;
  revisit after the first app wave (§3).

## 2. Greenfield developer API (Deliverable 2)

Two complete candidates were designed; both are encoded in
`api-prototype/api.ts` (candidate A fully; candidate B below).

### Candidate A — one write door with verb sugar (SELECTED)

The workspace exposes typed table handles with `create` / `update` /
`upsert` / `delete`, KV `get` / `set` / `clear`, reads `get` / `list` /
`has` / `count` / `observe`, one `transact(fn)` boundary, a SELECT-only
`sql(query, params, schema)` escape hatch with declared result validation,
`observeSql(tables, run)` invalidation, `docs.<table>.<doc>(rowId)` child-doc
handles, and `planImport(source)` for reviewable merges. Single-verb calls
are defined as one-operation instances of `transact`; there is exactly one
write path in the implementation.

### Candidate B — capability-split (REJECTED)

Reads live on an ambient `db` object; writes exist **only** inside
`write(fn)`; no verb methods outside the callback. Maximally honest about the
mutation boundary, but the census shows the dominant real write is a
one-liner (`update(id, {pinned: true})` shapes: 19+19+17 call sites across
`set`/`update`/`delete`); forcing every one-liner through a callback taxes
the 95% case to advertise an invariant the implementation can own invisibly.
Candidate A keeps the same single implementation door.

### Verb grill results

- `set` **dies**: with create, complete replacement, partial patch, and
  terminal deletion as distinct semantics, `set` is unreadable at the call
  site (the census shows it used both as create and as upsert today).
- `update` **survives** (19 production callers, exact partial-patch
  semantics; renaming to `patch` buys nothing over the incumbent).
- `upsert` **added** for complete-row create-or-replace (importers; the
  Reddit importer's actual intent at its `set` call sites).
- `delete` **survives** with terminal semantics.
- KV `delete`/`reset` collapse into `clear` (return to declared default).
- `connect(connection | null)` **dies**: local-vs-synced is an `openWorkspace`
  option, and enabling sync later is the explicit import flow, never a reopen
  flag.
- `transaction` → `transact`; `mutate` refused as a public name (the mutation
  is an implementation fact, not a user concept); `sql` survives as the
  explicit escape-hatch name.

### Method-to-storage / method-to-wire map (Deliverable 7)

| Public call | Local SQLite effect (one transaction) | Wire |
| --- | --- | --- |
| `create(row)` | INSERT typed row + outbox row + seq alloc | one mutation: `patchRow` (all cells) |
| `update(id, patch)` | UPDATE named cells + outbox + seq | `patchRow` (named cells) |
| `upsert(row)` | INSERT OR REPLACE + outbox + seq | `patchRow` (all cells) |
| `delete(id)` | DELETE typed row, INSERT tombstone + outbox + seq | `deleteRow` |
| `kv.set(k, v)` | UPSERT reserved kv row + outbox + seq | `patchRow(kv-namespace, k, {value})` |
| `kv.clear(k)` | UPSERT value=NULL + outbox + seq | `patchRow(..., {value: null})` |
| `transact(fn)` | all of the above accumulated | ONE mutation, N operations |
| `get`/`list`/`has`/`count`/`sql` | SELECT only | none |
| `observe`/`observeSql` | none (post-commit signal) | none |
| `docs.notes.body(id)` | Yjs update load from local doc store | Yjs plane (lazy) |
| `planImport(...).apply` | ordinary mutations via transact batches | ordinary `patchRow`/`deleteRow` |
| local-only open | identical minus outbox/seq/actor entirely | none |

Error semantics: writes throw typed errors on validation failure and on
create-over-live/tombstoned ids; reads return `null` for absence;
nonconforming stored rows surface in a diagnostic lane, never as exceptions
from `list`.

## 3. Schema ownership (Deliverable 3)

**`field.*` is the single canonical source** for TypeScript inference,
runtime validation, SQLite DDL, editor metadata, and import diffs. The
derivation graph is one-directional and all-runtime (no codegen):

```txt
field.* schema (JSON Schema at rest)
  ├─> Static<> row types            (compile time)
  ├─> Value.Check validators        (write API boundary)
  ├─> CREATE TABLE / CREATE INDEX   (loose DDL: PK only, see fold totality)
  ├─> editor widgets / import diff  (recognize())
  └─> list()/sql() result typing    (declared schemas at the call site)
```

**Drizzle is refused, with a written re-entry condition.** The 2026 layer
died as "a ~250-line type-level column walker … zero in-repo consumers"
(c84fd1f719) — a second derivation beside the real DDL path. The failure is
structural, not historical: field.* must stay canonical (editor metadata,
validation, and the schema-blind wire all read it), so Drizzle could only
ever re-enter as derivation #2 — the exact shape that died. What changed
(SQLite now canonical, queries real) creates consumers for *typed reads*, not
for a second schema system; typed reads are served by `list()` and
`sql(query, params, schema)`. Re-entry condition: a production app's query
corpus outgrows point reads + indexed lists + validated raw SQL, **and** the
Drizzle schemas are code-generated statics (no runtime walker), **and**
Drizzle Kit is not asked to consume runtime-generated tables (its migration
path expects statically discoverable schema modules).

Gaps to fix in field.* during the production wave:

- `field.json`'s static-type gate forces `Type.Unsafe` bypasses today (wiki
  `columnsCell`, `pageTypeValuesCell` — live counterexamples). Widen
  `field.json` (or its `defineTable` constraint) so nested-record statics
  survive; keep the raw escape hatch for genuinely irreducible shapes.
- Indexes move into `defineTable(columns, { indexes })` (0 producers today,
  but SQLite-canonical reads make them load-bearing immediately; the census
  found every `folderId`-style filter running as full scans through
  `scan().rows.filter`).
- UNIQUE/CHECK/FK constraints: refused as DDL (fold totality, §1.4).

## 4. Migration model (Deliverable 4)

Five version axes, five owners — never one number:

| Axis | Owner | Representation |
| --- | --- | --- |
| App SQLite representation | `defineWorkspace.version` + `migrations` manifest | integer revision; recorded in local meta table with schema-as-applied JSON |
| Logical synchronized data | breaking manifest entries | app-schema **major** = 1 + count of breaking entries (derived, ordered) |
| Client sync storage (`__epicenter_*`) | sync engine | one meta value (version **table/row**, not `PRAGMA user_version` — unsupported in DO SQLite; keep one mechanism on all three engines) |
| Server sync storage | server adapter migration list | same table pattern per engine |
| Wire protocol | request envelope `protocolMajor` | negotiated per connection, never per mutation |

Decisions:

- **Eager whole-database migration at open** replaces per-row `_v` +
  migrate-on-read. Census: 41/41 production tables single-version — the
  per-row machinery protects nothing real, hides failures inside reads, and
  its version diversity exists only because Yjs made rewriting expensive.
  SQLite makes eager rewrite ordinary. `_v` is deleted everywhere.
- The local DB records the applied revision **and the schema as applied**;
  on open with a newer definition, additive diffs (new tables, new nullable
  columns, new non-null columns with deterministic defaults) auto-generate
  DDL; anything else must be covered by that revision's hand-authored
  `apply(tx)` or the open fails loudly.
- **Breaking migration protocol:** bumping a major pauses older majors at
  the server (one schema-blind integer compare — the server stores the
  highest major that has written, no app schema knowledge). The first
  upgraded replica(s) run the deterministic, idempotent data transform as
  ordinary mutations under their own actor; racing upgraders converge because
  the transform is a pure function of row state. No named service actor, no
  server coordination.
- **Outbox rewrite at upgrade** (new, mandatory): a breaking local migration
  transforms pending outbox operations with the same mapping as rows, in the
  same transaction. Gate 3 gains directed traces for it.
- Old client while incompatible: local writes continue, sync pauses, upgrade
  reconciles. Downgrade: refused.
- Unknown additive fields are **compatibility state** (sidecar), not
  migration state; promotion into typed columns happens inside the eager
  migration transaction exactly once.

## 5. Client materialization and the canonical-shadow question (Deliverable re: Review 10)

Claim: **typed application tables + outbox + one replica-state row + a
tombstone table + an unknown-field sidecar are sufficient.** The refusals
make this provable, not just plausible: a pending mutation leaves the outbox
only when its effect is contained in accepted state (echo pulled in the same
transaction, or snapshot high-water ≥ its sequence). Therefore, at prune
time, the accepted value of every cell the pruned mutation touched equals
the value the typed table already shows if no later pending write covers it,
or is masked by that later pending write — which itself will only prune by
containment. The typed table never needs to reveal an accepted value from
under a live pending write, because pending writes are never discarded.

Deterministic traces (all satisfiable without a shadow):

1. Local patch X=B, push, ack lost → outbox retains; retry idempotent
   (seq ≤ high-water returns existing ack).
2. Remote same-cell X=R accepted before pending X=B: pull folds page, then
   **reapplies pending ops for touched rows in the same transaction** —
   visible stays B; echo later prunes; converged value = B everywhere.
3. Reverse acceptance order: echo prunes first (visible B), later remote R
   applies with no pending cover → visible R = server. Converges.
4. Different cells compose trivially (fold is per named cell).
5. Accepted echo + crash before/after prune: prune shares the pull
   transaction; reopen resumes from committed cursor; duplicate pages inert
   via cursor compare-and-swap.
6. Snapshot install with pending writes: one transaction replaces rows,
   prunes outbox by actor high-water, replays remaining pending mutations on
   top. Outbox stores whole mutations, so replay is total.
7. Terminal deletion racing a late pending patch: pending replay consults the
   local tombstone table and folds to no-op — this trace is what **earns the
   tombstone table** (reserved hidden columns on typed rows would resurrect
   shapes and break `NOT NULL`-free DDL less cleanly; a deleted row must not
   exist in the typed table at all).
8. Unknown additive field in a pulled mutation: routed to the sidecar —
   earns the sidecar, not a shadow.
9. Malformed/partial create: storable because synced DDL is loose (§1.4);
   classified at the read boundary.
10. Physical backup restore: stale actor sequence would reuse numbers with
    different payloads; the server's dedup silently drops them — which is
    why restore-while-original-lives requires import-as-new-replica, and why
    the restored-lost-replica path is the only sanctioned physical restore.

Gate 1 still runs both representations (the analysis above is an argument;
the gate is the proof), but representation B (typed-tables-only) is the
predicted winner and representation A exists to lose honestly.

Mathematical reference-model state vs physical storage: the reference model
may keep a canonical map — that is its job as the spec oracle. The physical
client keeps none.

## 6. Metadata keep/delete matrix (Deliverable 5)

| Name | Verdict | Invariant owned | Minimal deletion trace |
| --- | --- | --- | --- |
| `actorId` | KEEP (client-minted, server-registered on first push, not portable) | one mutation stream = one replica | delete → idempotency needs per-mutation UUID + unbounded server dedup set surviving compaction |
| `actorSequence` | KEEP (contiguous) | idempotency, outbox pruning via high-water, loss detection | delete contiguity → a dropped mutation is an undetectable silent hole |
| `nextActorSequence` | KEEP (one INTEGER in replica state, allocated in the write transaction) | no reuse across crash | "derive from outbox max + accepted high-water" stores the same integer with two owners |
| `serverSequence` | KEEP | the only conflict clock; cursor space | delete → no acceptance order exists |
| `pullCursor` | KEEP (integer; advances only in the page-apply transaction) | "everything ≤ N durably folded" | advance outside the transaction → crash re-applies or skips a page |
| `databaseGeneration` | RENAME to `databaseId`, server-minted at database creation | client cursors/outboxes are meaningless against a recreated database | delete → account reset + old cursor = silent divergence. Client-side dbGen/sessionGen counters from the gates design: DELETE (volatile connection epoch suffices) |
| `snapshotGeneration` | KEEP, bootstrap-scoped | chunks must not mix builds; one published + one building | delete → a client can install chunk 1 of build N and chunk 2 of build N+1 |
| app schema major | KEEP (request envelope + one schema-blind integer per database) | pauses incompatible writers | delete → old-major client writes renamed-away cells forever |
| local schema revision | KEEP (client meta only) | eager migration idempotence | — |
| client/server sync-storage versions | KEEP as meta-table rows (NOT `PRAGMA user_version`; unsupported in DO SQLite) | internal DDL evolution | — |
| `protocolMajor` | KEEP once per request envelope; DELETE from Mutation | encoding negotiation | per-mutation copies are dead weight in every outbox and log row |
| mutation UUID | **DELETE** | none beyond (actorId, actorSequence) | retry/dup/lost-ack → seq dedup; clone/restore → new-actor flow; queue workers → authority allocates seq atomically. A UNIQUE index "for defense" is the retained-metadata smell |
| actor high-waters | KEEP (server; inside snapshots) | idempotency + outbox pruning across compaction | delete → compaction erases dedup state; re-push duplicates history |
| compaction watermark | KEEP (one integer) | "cursor too old → snapshot required" | delete → stale client pulls a hole |
| snapshot checksum | KEEP (SHA-256 manifest + per chunk) | corruption refuses install | FNV-style non-cryptographic digest keeps silent corruption classes |
| tombstones | KEEP forever (both sides; in snapshots) | terminal identity; no resurrection | delete → late patch resurrects a deleted row as a ghost |

Sizing note (from DO grounding): mutations and snapshot chunks must respect
the Durable Object 2 MB row cap — the protocol's bounded-mutation-bytes and
chunk-size limits are platform-required, not optional hygiene.

## 7. Operation language (Deliverable 7, wire side)

`patchRow` / `deleteRow` survive every reduction and every extension attempt:

- Split `create` from `patch` on the wire? Dies: create-on-unknown is what
  makes logical import idempotent and lets two devices import the same
  stable row id.
- Whole-row `replace` op? Dies: expressible as patchRow naming every cell;
  a dedicated verb would let old clients erase unknown fields.
- KV verb? Dies: reserved namespace + `value` cell (ADR-0120), confirmed.
- Multi-row/multi-table atomicity? Owned by the mutation envelope, not ops.
- Set-based server ops (`UPDATE WHERE`)? Refused: the server is schema-blind
  and must not evaluate predicates; bulk local writes enumerate ids through
  `transact`.

The local API is deliberately richer than the wire (create/update/upsert
distinctions are validation semantics, not wire semantics) — hiding them
would contort the app surface to mirror transport, the exact inversion the
mission forbids.

## 10. Falsification-gate review (Deliverable 10)

Common-mode risks in the current gate design and required strengthenings:

- **Common-mode error risk:** the reference fold and the SQLite engines must
  be written by different construction (the gates doc already promises
  independent SQL implementations — keep that, and add that the *pull
  applier* (fold + pending replay) must also be implemented twice, since it
  is where §5's argument could fail in practice).
- **Missing directed traces (added to the spec):** outbox rewrite across a
  breaking migration; snapshot install where pending mutations touch
  tombstoned rows; unknown-field sidecar collision with a concurrent typed
  promotion; backup-restore actor-sequence reuse (must be *detected* as the
  import-as-new-replica precondition, not silently deduped).
- **Deterministic schedules:** the seeded generator must derive every random
  choice from the seed (the existing design does this); crash points must
  enumerate *every* durable boundary programmatically rather than a
  hand-picked list, or a new boundary added later silently escapes testing.
- **Minimized counterexamples:** required output of a failing seed is the
  shortest directed trace, not the seed alone.
- **Stop condition:** each gate stops on either all-traces-pass or a minimal
  counterexample that names the earned mechanism (e.g. "this trace earns a
  canonical shadow"); gates must not add mechanisms speculatively.

# Pass 3 (2026-07-11, same day): schema epochs, boundary imports, and the corrected API

Third, focused decision pass. Inputs: this memo (passes 1-2), the independent
second review's ten blockers, and four bounded adversarial evidence seams run
through Codex (epoch-model adversary, merge-planner state machine, actor
restore and snapshot freeze proof, nonconforming-row query semantics). This
addendum SUPERSEDES: §2's verb selection and `openWorkspace({ sync? })`, §4's
breaking-migration model including the outbox-rewrite rule, the §6 rows for
`databaseId` and app schema major, and the §12 Gate 1 handoff envelope. The
spec and the three Proposed ADRs are edited to match; this section records why.

## 13. Decision memo

### The final one-sentence product contract

Each Epicenter app keeps a complete local SQLite replica of one database that
lives in exactly one schema epoch; every write inside the epoch synchronizes
silently under server acceptance order, and everything that crosses a database
boundary (sign-in, restore, endpoint movement, epoch upgrade) arrives through
one reviewable import applied as ordinary mutations.

### What changed and why

1. **In-place breaking migration is deleted; schema epochs replace it.**
   Pass 2's model (count-derived major, server pauses lower majors, first
   upgraded replica transforms shared rows in place, client rewrites its
   pending outbox) died on three blockers: transforms do not commute with
   concurrent new-schema writes, arbitrary pending patches cannot generally
   be transformed, and a count is not a compatibility identity (two
   incompatible forks can both claim "major 2"). The epoch adversary seam
   attacked the replacement across additive, rename, split, merge,
   ID-changing, and narrowing scenarios and found NO counterexample that
   forces in-place migration back. This pass's own §4 "outbox rewrite at
   upgrade (new, mandatory)" is therefore also deleted: the outbox is never
   rewritten, because after the freeze barrier its effects are already in the
   local tables the transform reads.

2. **The epoch id is authored, the incarnation id is minted.**
   `schemaEpochId` is an opaque string written into the migration manifest
   (initial epoch in `defineWorkspace`, a new id on each breaking entry), so
   compatibility identity is migration lineage, not arithmetic. The
   schema-blind server compares it as an opaque string. `databaseId` is
   renamed `databaseIncarnationId`; a new epoch or an account reset mints a
   new incarnation, and actors, cursors, outboxes, and snapshots bind to it.
   Honesty note: an authored id cannot prove a developer minted a new one
   after a breaking edit; the recorded schema-as-applied is the lint (a
   non-additive diff without an epoch entry fails the open loudly).

3. **The identity rule is the asymmetric win of this pass.** Every
   resurrection counterexample the adversary found (email-keyed ids, split
   tables keyed by `hash(address)`, handle-derived ids across skipped epochs)
   shares one cause: new-epoch identities derived from mutable cell values,
   which tombstones cannot supply. Refusing exactly that — output
   `(table, rowId)` derives only from input `(table, rowId)` — makes every
   tombstone mappable, closes every resurrection trace, keeps skipped-epoch
   transform composition safe, and deletes the retirement-ledger mechanism
   that would otherwise be required. Splits stay expressible
   (`'address:' + rowId`); many-to-one merges are refused this wave because
   two independent deletion states cannot share one terminal identity.

4. **Epoch cutover is fenced, and the order is load-bearing.**
   Freeze old incarnation at head H; the upgrader pulls THROUGH H and replays
   its own pending writes locally BEFORE transforming (otherwise accepted
   writes it has not pulled are stranded: the adversary's rename trace loses
   an accepted `color = "blue"`); the new incarnation is `preparing` and
   invisible until its baseline is sealed (otherwise a second upgrader
   auto-applies against a half-imported baseline and silently loses reviewed
   intent); then it activates. Racing upgraders converge because
   identity-derived transforms of identical state diff to nothing.

5. **Actor-preserving restore is deleted.** The restore seam proved its
   safety preconditions are user promises, not software: the server owns a
   high-water and an acknowledgement, so it cannot distinguish "restored lost
   replica" from "live clone", and a restored file reusing an accepted
   sequence number with a different payload is silently swallowed. Every
   physical restore or copy opens as an import source under a new actor.
   Crash-reopen of the same durable file is NOT a restore (sequence dedup
   absorbs the retry). Value-level double-apply is neutralized by the diff
   when the destination is unchanged, and surfaces as an honest reviewable
   difference when a third device wrote in between.

6. **Quarantine is the provisional nonconforming-row representation.** The
   query-semantics seam showed the permissive alternative makes
   `sql('SELECT count(*)')` and `list().length` silently disagree, and that
   renaming sql "physical" is honest but not safe (developers will still
   join and count with it). Quarantine gives `sql` and `list` one row
   population by construction; it is derived local state, never on the wire;
   cross-revision lane placement may differ between replicas without
   divergence. It does not block starting Gate 1; its traces are assigned to
   Gates 1 (completion promotion), 2 (snapshot reclassification), and 3
   (cross-revision placement).

7. **Additive tables join additive fields.** Reversing the pass 2 provisional
   refusal: under epochs a breaking change costs a full import on every
   device, which prices "added a table" absurdly. An unknown-row lane
   (whole rows by `(table, rowId)`, tombstone store accepting unknown table
   names, transactional identity-preserving promotion) keeps old clients
   complete replicas. Exports and epoch transforms must read the COMPOSED
   row: typed cells + sidecar + unknown rows.

8. **Snapshot freeze is one invariant.** Rows, tombstones, AND actor
   high-waters are captured from one read state at one sequence S; a builder
   that reads high-waters at a later head publishes a snapshot that prunes a
   pending mutation its rows never folded (permanent silent loss). Ordinary
   pull pages prune only exact echoes and never carry a head high-water a
   client could prune by. The stale `gates/DESIGN.md` traps (`compact(upTo)`
   at arbitrary historical sequences; `lastClientSeq` returned on normal
   pages) are named in the Gate 1 handoff below and die in the rewrite.

## 14. Schema-epoch lifecycle

```txt
                         one (principal, app) family
                         ───────────────────────────

  Epoch E1 / incarnation I1 (ACTIVE)
    replicas A, B, C sync normally; additive revisions migrate
    eagerly in place; unknown fields/rows ride the lanes
        │
        │  app ships a breaking revision (epoch entry: id E2, transform T)
        ▼
  I1 FROZEN at head H (read/export only)
        │
        │  upgrader A: pull through H ─► replay own pending locally
        │              ─► T(composed logical state: cells+lanes+tombstones)
        ▼
  Epoch E2 / incarnation I2 (PREPARING: only creator writes, invisible)
        │  baseline sealed and verified
        ▼
  I2 ACTIVE ── new actor set; A,B,C re-join by bootstrap or import
        │
        ├─ replica B (no divergence): bootstraps I2 snapshot; done
        ├─ replica C (offline with pending writes, returns later):
        │    local replica stays READABLE + EXPORTABLE in E1;
        │    upgrade composes T across any skipped epochs and enters
        │    I2 through the ordinary import plan (auto where equal,
        │    review where both sides changed); old outbox dies
        │    unrewritten with I1
        └─ I1 retired when no replica needs it (export always possible
           while retained)

  Local-only workspace: same epoch entries, but exactly one writer exists,
  so T applies eagerly in place at open; no freeze, no import.
```

## 15. Database import lifecycle (one planner, every boundary)

Boundaries: local-to-account promotion, restore/backup adoption, physical
clone adoption, Cloud to self-host, self-host to Cloud, old epoch to new
epoch. Never background sync.

```txt
pin source logical snapshot ──► optional identity-preserving transform
    ──► preflight (injectivity; collisions are plan errors that block apply)
    ──► compare with pinned destination snapshot
    ──► plan ──► apply (revalidates destination head; changed cells re-diff)
    ──► ordinary patchRow/deleteRow + Yjs update application
    ──► source retained until destination durably accepts
```

Automatic (no review):

- destination empty (zero rows AND zero tombstones from one consistent
  snapshot): stream the import, skip diff construction entirely
- source-only rows and source-only cells: additions
- equal cells and equal tombstones: no-ops
- source tombstone over destination-absent: carried as deleteRow
- destination-only rows and cells: untouched (absence is not deletion)

Bulk preference with reviewable list:

- same cell, different values (source vs destination)
- source tombstone over destination-live row (take source = terminal delete)

Review-required:

- source-live row over destination tombstone: the delete wins by default;
  restore only under a NEW row id (patchRow on a tombstone folds to no-op,
  so the plan cannot lie about resurrection)
- bodies with unrelated Yjs histories: keep destination or merge histories
  (source-only replacement refused until a document-reset contract exists)

Plan errors (block apply):

- transform maps two source rows to one target id
- source snapshot unreadable or inconsistent

Bodies ride the same plan as a row-gated second lane: destination-absent
copies, shared history auto-merges via Yjs update application, excluded rows
suppress their bodies, restored-as-new rows remap their bodies to the new id.

V1 surface: planner + summary counts + bulk preference + the review lists.
A per-cell editor UI is built only when real review volume earns it.

## 16. Public API (final proposal, type-checked in api-prototype/)

```txt
Declaration
  defineWorkspace({ id, name, version, epoch, tables, kv, migrations })
  defineTable(columns, { indexes, docs })
  defineKv(schema, defaultFactory)        // schema must not admit null
  migrations: { 2: { apply? },            // additive: eager in-place DDL
                3: { epoch: { id, transformRow, transformTombstone? } } }

Opening (two doors, not one option)
  openLocalWorkspace(def, { storage })            // no actor/cursor/outbox
  openReplica(def, { storage, sync })             // current-epoch replica
  planEpochUpgrade(def, { storage, sync })        // superseded-epoch door

Reads (workspace and tx)
  t.get(id) / t.list({ where, orderBy, desc, limit }) / t.has / t.count
  ws.sql(select, params, schema)   // one row population with list()
  t.observe(cb) / ws.observeSql(tables, run)      // conservative invalidation

Writes (wire-honest verbs; each call = one atomic mutation)
  t.put(row)        // complete declared row, create-or-replace
  t.patch(id, cells)// named cells of a live row; null when absent/deleted
  t.remove(id)      // terminal
  ws.transact(fn)   // the one write door; verbs are one-op instances

KV
  kv.get(key) / kv.set(key, value) / kv.clear(key)  // clear = wire null

Child docs
  docs.notes.body(rowId) -> disposable handle (Y.Text | Y.XmlFragment)

Boundaries
  ws.planImport(source) -> ImportPlan    // file | export bytes | workspace
  ws.exportSnapshot() -> bytes           // rows+content, never identity
  plan.apply({ prefer?, overrides?, readdDeleted?, excludeRows? })
```

Verb grill, pass 3: `create` and `upsert` die with `set`. The fold
create-merges on unknown ids (that is what makes import idempotent), so
globally exclusive creation is not a promise the wire can keep; and
"complete replacement" cannot touch unknown additive fields, so upsert also
overpromised. `put`/`patch`/`remove` are the local images of
patchRow-all-declared-cells, patchRow-named-cells, and deleteRow. Local
double-submit guards are `has()` inside `transact`. Nullable KV is refused
because the wire encodes clear as `value: null`; absence semantics belong to
the default factory.

# Pass 4 correction: exact schemas and recoverable cutover

This focused correction applies the user's approved exact-schema refusal and
supersedes pass 3 wherever it allowed additive logical revisions inside one
epoch. It also closes the cutover-ownership and transform-cardinality gaps found
after reading the pass as a proposed final architecture.

## 21. Corrected final contract

Each database incarnation synchronizes one exact logical schema under server
acceptance order; every logical schema change creates a new incarnation whose
canonical baseline comes from a recoverable server-owned epoch transition, and
every replica carries private divergent intent across the boundary through the
one logical import planner.

### Exact means exact

`schemaEpochId` is derived from the complete canonical synchronized schema plus
the ordered authored semantic epoch lineage. Adding a table, adding a field,
widening a select, changing nullability, changing meaning, or changing a
transition transform creates a new identity.
Indexes, query plans, and internal SQLite encodings do not. This deliberately
refuses invisible cross-version synchronization in the first implementation.

Deletion prize:

- unknown-field sidecar;
- unknown-table row lane;
- promotion and cross-revision placement rules;
- additive-schema Gate 3;
- the unresolved select-widening policy.

Structurally valid but invalid or unknown input from a buggy client remains a
single problem: nonconforming logical rows. The provisional quarantine candidate
owns that whole exceptional row. Gate 1 still compares quarantine with
permissive application tables and a complete canonical shadow; this memo does
not declare the physical representation proven.

### One transform owns identity

The pass 3 prose allowed one-to-many splits while its prototype returned at most
one row. V1 now refuses both one-to-many and many-to-one transforms. One
`mapIdentity(source)` function maps a source `(table, rowId)` to zero or one
target identity and is used unchanged for live rows and tombstones. A separate
`transformCells(row, target)` may change values but cannot choose identity.
This collapses `transformRow` plus `transformTombstone` and makes terminal-delete
preservation one invariant with one owner.

### Cutover belongs to the server authority

```txt
ACTIVE I1
  -> begin(expected I1, target schema identity)
  -> FROZEN I1 at canonical head H
  -> PREPARING I2 under an expiring transition lease
  -> transform canonical snapshot at H
  -> seal and verify I2 baseline
  -> atomically activate I2; retire I1

abort or lease expiry before activation
  -> delete partial I2
  -> unfreeze I1
```

The global baseline never includes the initiating replica's private pending
overlay. This makes preparation reproducible and resumable by another
authenticated device. After I2 activates, every replica, including the
initiator, transforms its visible local state and imports only its difference.
Equal canonical content is a no-op; private pending intent appears honestly in
the ordinary import plan.

The server remains schema-blind. It owns only opaque identities, the expected
active-incarnation compare-and-swap, freeze head, transition lease, preparation
state, and atomic activation. The authenticated principal may initiate, resume,
or abort the transition.

### Corrected developer wording

`put(row)` writes every cell declared by the exact schema. It is not row
replacement, and the wire still has no replace operation. `patch` and `remove`
retain their pass 3 meanings. Local and replica opening remain separate doors.
The input no longer repeats `version` beside a numbered migration record:
`migrations` is an ordered array and the local storage revision is derived as
`1 + migrations.length`.

The generic planner also drops pass 3's `readdDeleted` option. Restoring a live
source row over a destination tombstone requires a new id and may require
remapping inbound references, which current runtime field metadata cannot do
safely. V1 lets the deletion win and leaves restoration to an app-owned copy
flow rather than exposing a misleading generic switch.

### Corrected build order

```txt
Gate 1: one exact schema, one incarnation, client representation
  -> Gate 2: snapshot and compaction at one frozen sequence
  -> Gate 3: exact schema fencing and recoverable epoch transition
  -> import planner and minimal review surface
  -> production workspace API clean break
```

The final remaining product-taste questions are verb spelling, Bun-first versus
simultaneous runtime adapters, actor limits/revocation, and the eventual planner
name. Schema widening is no longer a taste question in V1: it creates a new
epoch.
