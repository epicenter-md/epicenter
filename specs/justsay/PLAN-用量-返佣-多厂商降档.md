# 能说会道 · 用量 / 返佣 / 多厂商降档 规划

> 本文汇总三大板块:① 使用量(免费额度 + 成本安全)、② 邀请返佣、③ 多厂商与降档路由。
> 外加支撑性补充:成本模型、定价档位、接口契约影响、配置项总表、合规清单、监控指标、路线图、未决问题。

## 0. 成本模型(一切的地基)

先确立单位经济,后面免费额度、定价、返佣比例都从这里推。

```
单价(豆包小时版,阶梯):
  30h ¥28(¥0.93/h) · 1000h ¥900(¥0.90) · 10000h ¥8800(¥0.88)
  100000h ¥85000(¥0.85) · 300000h ¥240000(¥0.80)

并发版:¥500 / 并发 / 月。盈亏平衡 = 568h/月/并发 ≈ 78% 利用率才划算。
  → 消费级爆发式流量,单槽利用率 5~20%,远不到 78%。结论:用小时版,不买并发版。
  → 截图里「并发限额 50」是小时版默认天花板,提额走工单,不是去买并发版。
```

每用户成本(免费档 10000 字/周):

```
10000 字/周 ÷ ~225 字/分 ≈ 44 分钟音频/周 ≈ 3.2 小时音频/月

项                  单周        单月
ASR(¥0.85/h)       ¥0.63       ¥2.7
成文 LLM(DeepSeek)  ~¥0.02      ~¥0.1
翻译                ~¥0.03      ~¥0.15
随便问              ~¥0.05      ~¥0.2
合计                ~¥0.7       ~¥3
```

**核心洞察:COGS ≈ 100% 是 ASR 音频时长。** 翻译 / 随便问 / 成文的大模型钱是零头。
含义:免费额度成本 ~¥3/活跃用户/月(兜得住);翻译 / 随便问按价值收费(成本几毛);
压成本唯一路径 = 压 ASR 单价(走高档时长包 / 自建 SenseVoice 削峰)。

规模参照:5000 DAU 全用满免费额度 ≈ **¥1.5 万/月 ASR**。

并发承载(Erlang B,50 路 @ 1% 阻塞 ≈ 37.9 Erlang):

```
忙时活跃用户上限 ≈ 37.9 × 60 / (日音频分钟 × 忙时占比)
日音频 5.7 分钟、忙时占比 10~15% → 忙时可并发 ~2700~4000 用户 → 估 DAU ~5000~8000
注:非线性,并发翻倍价值更高(100 路 @1% ≈ 84 Erlang)。
```

自建 SenseVoice 兜底(阿里云 A10 ~¥4000/月):

```
利用率      月处理音频     折算单价       对比豆包 ¥0.8/h
50%         18,000 h       ¥0.22/h        便宜 3.6 倍
30%         10,000 h       ¥0.40/h        便宜一半
14%          5,000 h       ¥0.80/h     ← 盈亏平衡点
盈亏平衡 ≈ 1560 活跃用户;单卡 well-utilized 覆盖 ~5000 活跃用户。
→ 临界 ~1500~2000 用户后自建才比豆包便宜;早期纯豆包按量。
→ 当前那台上海 2c2g 纯 CPU,只能跑大脑 + dev 验证,不能跑生产 ASR。
```

## 1. 板块一:使用量(免费额度 + 成本安全)

核心是**双闸**:字数闸给用户看,成本闸防刷。

```
┌─ 闸 1:字数额度(产品面,用户可见)────────────────┐
│ 注册即享 10000 字/周(Typeless / Tabplus 都是 8000,我们 10000)  │
│ 每周一 00:00 重置(Typeless 是周一 07:00 UTC)                  │
│ 转写成文消耗字数;翻译 / 随便问 = 会员功能,默认不吃这个池子    │
│ free_weekly_chars 做成全局配置 + 可按用户覆盖(发奖励 / 提额用)│
└────────────────────────────────────────────────┘
┌─ 闸 2:成本安全闸(后台,防技术刷量)────────────────┐
│ 每用户硬上限:≤ ¥1/周、≤ ¥5/月(可配)                      │
│ 按真实成本累加:ASR 秒数×单价 + LLM token×单价               │
│ 哪个先到先拦:正常用户字数先到,刷子成本先到                  │
└────────────────────────────────────────────────┘
```

为什么两层:字数计数可能被钻空子(超长音频、脚本调接口),
**¥5/月 成本硬闸是兜底,刷子最多让你亏 5 块就被掐断**。10000 字/周 ASR ≈ ¥0.63,
所以 ¥1/周 闸基本不误伤真人。

**拦截顺序(免费用户,每次请求)**:

```
1. 周字数 < 限额  且  周成本 < ¥1  且  月成本 < ¥5 ?
2. 否 → 拦截 / 降级,弹「升级」
3. 是 → 成功后【原子】累加 chars_used + cost_cents(按实际)
```

**展示(侧边栏条,照 Typeless 截图复刻)**:

```
GET /quota → { chars_used, chars_limit, reset_at, plan }
UI:  [▓▓▓░░░░░░░] 495 / 10000 字 ⓘ
     ⓘ tooltip:「每周可获 10000 免费字数,每周一 00:00 重置」
     [升级] → 无限字数 + 增强准确性 + 高峰优先
```

**防刷(成本闸之外)**:

```
· 单条音频时长上限(如 60s)→ 防超长音频刷
· QPS / 每分钟请求数限制
· 实名注册(微信 / Apple / 手机号唯一)→ 抬高批量注册成本
· 新号冷却 + 异常检测(用量突增、机器规律间隔)
```

## 2. 板块二:邀请返佣

### 2.1 合规红线(决定架构,不能踩)

```
· 微信支付只允许「两级分销(含平台本身)」→ 实际就是【单层返佣】:
    平台 → A(推广人) → B(付费)
    A 只能从「自己直接邀请的 B」拿佣金;不能再从 B 邀请的 C 抽成(那是三级 = 封支付)
· 返佣比例法定 ≤ 50%(我们用 20~25%,远低于线)
· 「终身返利 / 排队返利 / 金字塔提成」= 微信明确不支持类目 → 返佣必须【限期】
· 数据层把单层写死(Referral 不存祖先链),从结构上杜绝多级
```

参照 Typeless affiliate:25% 经常性返佣、但只返【首年】、PayPal 美元、
**只对桌面 checkout 返佣,App Store / Google Play 内购不返**(苹果谷歌抽 30% 且不配合分账)。

### 2.2 两条奖励线

```
线 A · 邀请得代金券(拉新,低价值)
  好友通过你的码注册 + 完成首次有效口述 → 你得 ¥5 代金券(抵月费)
  · 要求「有效使用」而非光注册 → 防注册刷
  · 月度上限(如每月最多领 ¥50 邀请券)+ 有效期(如 90 天)

线 B · 分销返佣(拉付费,高价值,recurring)
  你直接邀请的好友付费 → 你按比例拿返佣(单层!):
    ¥10/月 档 → 返 20% = ¥2 ；  ¥50 高档 → 返 25%
  · 单层:只返直接下线
  · 限期:学 Typeless 只返「首年」或「前 6 期」→ 避开终身返利
  · 返佣发「账户余额 / 代金券」抵会员费(内循环),不发现金
```

**返佣发代金券不发现金(三重好处)**:

```
1. 合规:不碰现金提现 = 不需支付牌照、不涉个税代扣、微信风控友好
2. 成本低:代金券只在【兑换时】按边际成本计,不是按面值掏现金
3. 留存:逼推广人回来续费用产品
(现金提现后置,规模化再上,届时做个税代扣 + 资金合规)
```

### 2.3 经济账(确认兜得住)

```
档位 / 渠道          售价   到手   ASR成本  返佣      净利
¥10/月 · 微信web     ¥10    ¥10    ~¥3     ¥2(券)   ~¥5
¥10/月 · 苹果IAP     ¥10    ¥7     ~¥3     ¥2(券)   ~¥2
¥50/季 · 微信web     ¥50    ¥50    ~¥9     ¥12.5(券) ~¥28
```

> iOS 内购被苹果抽 30%,叠加返佣后利润薄。能引导走微信 / 网页 checkout 的尽量走。

### 2.4 反作弊

```
· 防自邀请:同设备指纹 / 同支付账号 / 同实名 → 不计奖励
· 返佣触发点 = 下线「真实付费」,不是注册
· 注册券有月度上限 + 有效期
· 单层强约束写死在数据层
```

### 2.5 额外杠杆(可选)

邀请奖励除代金券,也可给「**周字数额度 +2000 字**」:不用零成本,用了更深参与,
比发钱划算。正好用上 `free_weekly_chars` 的按用户覆盖能力。

### 2.6 返佣结算与冻结期(防套利,必须)

套利漏洞:自己换设备邀请 → 付费 → 立刻拿返佣 → 退款窗口内退款 → 净赚返佣。
所以返佣不能「付费即结算」,要加冻结期 + 退款追回(clawback)。

```
· 佣金 T+N 冻结(如 7~15 天,覆盖退款窗口)→ 过冻结期才可用 / 可抵扣
· 下线退款 / 退订 → 自动追回对应佣金(冻结中直接扣,已发的从余额冲)
· 代金券内循环让追回简单:扣余额即可,不涉现金回款
· 返佣只对【实付现金订单】计:用代金券抵扣的订单不再产生返佣(防代金券循环套返佣)
· 结算流水留痕:Commission 表记 order_id + status(冻结 / 可用 / 已追回)
```

### 2.7 其他规则(占位,后续细化)

```
· 封禁 / 风控处置:检测到刷量后的分级动作(告警 → 限速 → 冻结奖励 → 封号)
· 代金券叠加规则:免费额度 + 代金券 + 返佣 是否可叠;防叠加套利(同一单只享一种最优)
· 取消订阅 / 客诉:退订后会员权益失效时点(到期失效 vs 立即失效 + 按比例退)
```

## 3. 板块三:多厂商与降档路由

### 3.1 先纠认知:流式 ≠ 更准

```
流式实时:  低延迟、边说边上屏    准确度【略低】(上下文不全)
文件识别:  说完才出、慢 1~2s     准确度【更高】(整句全上下文)
```

**「流式 → 文件」降级丢的是速度,不丢准确度,反而可能更准。**
所以高峰降级对质量几乎无损。真正要保实时流的只有**键盘实时上屏**;
App 内口述 / 翻译 / 随便问说完再出完全可接受,天然适合文件识别削峰。

### 3.2 分层降级阶梯

```
T0  豆包流式 2.0(实时流)      最低延迟 · 占并发槽 · 给会员 / 键盘
      │ 流式水位满 / 免费高峰
      ▼
T1  豆包录音文件识别 2.0        慢 1~2s · 按量无并发约束 · 削峰主力(还更准)
      │ 豆包故障 / 超配额 / 限流
      ▼
T2  备用厂商(阿里通义 / 讯飞)  主厂商熔断时切换,容灾
      │ 厂商全挂 / 要压成本
      ▼
T3  自建 SenseVoice(GPU)       成本兜底 + 终极容灾(不依赖外部)
      │ 全部饱和
      ▼
T4  短排队 / 降级提示           「高峰期,慢一点点」,绝不崩
```

### 3.3 调度决策(三输入)

调度器(ASR Router)挡在 `/v1/audio/*` 前,看三件事:

```
输入 1  实时流水位   当前流式并发 / 上限(如 80% 触发降级)
输入 2  用户等级     会员 > 免费(付费点)
输入 3  厂商健康     每家 成功率 + p95延迟,熔断 / 半开探测恢复

决策(键盘实时请求 r):
  if 流式水位 < 80%              → T0 豆包流式
  elif 会员 and 水位 < 硬上限     → T0(会员保实时)
  else(水位满 / 免费高峰)        → 降级 T1 文件 + 弹「高峰降速」
  叠加厂商健康:豆包熔断 → T2;全挂 → T3
```

**会员优先 = 直接对上截图卖点**:

```
会员:  高峰也保 T0 流式 + 豆包大模型高准确度 + 优先调度
免费:  平峰能流式,高峰先降 T1 文件(慢一点,不降质)
        → 正好是「增强准确性 + 高需求期间的优先访问」
        → 高并发不是纯成本,而是逼出付费动机
```

### 3.4 多厂商主备 + 两套策略

```
ASR:  豆包(主) + 阿里通义 / 讯飞(备 1 家) + 自建 SenseVoice(兜底)
LLM:  DeepSeek(主) + 豆包 / 通义(备)

两套路由策略(按请求性质分流):
  延迟敏感(键盘会员):  先挑最快 → 豆包流式,贵也走
  延迟可容忍(批量/免费): 先挑最便宜可用 → 自建GPU闲置 → 豆包文件 → 备用厂商
```

意义:容灾 + 削峰溢出 + 不被单厂商限流 / 涨价绑死。

### 3.5 方案对比(选 B)

```
方案                成本          体验        容灾    运维   评
A 全流式堆并发      高(养闲卡)   好          差      低     贵且脆
C 全文件识别        低            键盘体验差  差      低     省钱难用
D 自建为主          最低          中          中      重     早期不划算
B 分级路由+优雅降级  可控(按档摊) 好(会员保) 强      中     ✅ 推荐
```

B 一次性解决效率 / 准确度 / 成本 / 容灾 / 变现,且每档可降级,任一环挂了不崩。

### 3.6 落地影响

```
· 大脑:/v1/audio/* 前加 ASR Router 组件
        = 并发计数器 + 厂商健康表(熔断 / 半开) + 路由策略(可配)
· 端:键盘走 WebSocket 流式端点;流式槽满时服务端内部缓冲 → 文件识别兜底
      其余走 POST 文件端点。客户端始终只调一个接口,后端自己选 backend
      → 降级对端透明,维持瘦客户端
· 全做成配置,不写死(水位阈值 / 各档开关 / 厂商优先级 / 会员策略)
```
