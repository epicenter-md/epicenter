2. The request that has both● Established

Session cookienames principal A

Read first at line 138. Returns immediately and decides the principal for the whole request.

Bearer tokennames principal B

Never reached. parseBearer does not run, and nothing logs that the header was on the request.

Two credentials naming two different principals resolve silently to one. Nothing in the path records that the second one was there.

3. The fork▲ Unresolved

Precedence is the guarantee

Cookie-first is the intended contract. A browser session should win over a token the page happens to carry, and silence is correct.

Ambiguity is the bug

Two principals on one request is a caller error. The boundary should refuse it rather than pick, because picking hides a mistake upstream.

The code is compatible with both readings. Nothing in the file, the tests, or the surrounding comments distinguishes them.

The open question

Is preferring the cookie the guarantee, or is a request carrying both a request to refuse?
