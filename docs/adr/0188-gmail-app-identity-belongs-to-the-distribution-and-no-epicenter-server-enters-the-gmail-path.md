# 0188. The Gmail application identity belongs to the shipped distribution, and no Epicenter server enters the Gmail path

- **Status:** Accepted
- **Date:** 2026-07-29
- **Relates:** [ADR-0082](0082-local-mail-syncs-by-push-free-history-list-polling.md) (originally carried this decision on the wrong axis; retains push-free polling), [ADR-0081](0081-per-upstream-oauth-concurrency-decides-mirror-topology.md) (a per-device grant is free under Google's concurrency ceiling, which is what makes device-local consent affordable), [ADR-0071](0071-oauth-is-hosted-only-a-custom-instance-requires-a-token.md) (Epicenter's *own* OAuth is hosted-only; that is a different credential from the Gmail grant and does not govern here), [ADR-0116](0116-local-mail-is-desktop-first-one-bun-engine-no-background-mail-service.md) (the local engine that holds the grant), [ADR-0062](0062-local-books-stores-oauth-tokens-in-a-single-0600-file.md) (the 0600 on-disk token lineage this follows), [ADR-0068](0068-privacy-is-a-deployment-not-a-product-feature.md) (privacy is where you run it)

## Context

ADR-0082 decided that once each device talks to Gmail directly, the only remaining difference between hosted and self-hosted Epicenter is which Google OAuth Client ID fronts the consent screen: hosted would default to Epicenter's verified client, and a self-hoster would substitute their own.

That axis is wrong, and it is worth naming why, because the mistake is easy to repeat. Gmail traffic is device-to-Google. Which Epicenter instance a user selects (Epicenter Cloud, a self-hosted instance, or no Epicenter server at all) has no bearing on Google's consent screen, because no Epicenter server is in the Gmail path to begin with. ADR-0071 does make Epicenter's own OAuth hosted-only, but that governs the credential a user signs in to *Epicenter* with; reasoning by analogy from it is what produced the wrong axis. Under ADR-0082's shape, a user running the official signed app who moved their Epicenter data to their own box would suddenly owe Google a Cloud project to read their own mail, for no technical reason.

The axis that actually exists is who ships the binary. A signed distribution can carry a Google-verified application identity, because Google binds a verified consent screen to an app it has reviewed. A fork or a rebrand cannot legitimately present that identity, because the consent screen names who the user is trusting.

Local Mail originally made every build bring-your-own: `GMAIL_CLIENT_ID` and `GMAIL_CLIENT_SECRET` were required, so an ordinary user had to create a Google Cloud project before reading their own mail. The native shell can now compile in the distribution's identity while preserving those names as the machine-wide override. No official Epicenter Google client is provisioned in this repository yet, so the product promise still has an external release prerequisite.

## Decision

**The Google application identity Local Mail presents is a property of the distribution that shipped the binary, never of the Epicenter instance the user selected, and every Gmail effect stays on the device.**

1. **The official signed Epicenter distribution supplies one Epicenter-owned, Google-verified Desktop OAuth client automatically.** This applies identically whether the user selects Epicenter Cloud, a self-hosted Epicenter instance, or no Epicenter server at all. Selecting where your Epicenter data lives never changes where your Gmail consent goes.
2. **A source build, a fork, or a rebranded distribution supplies its own Google Desktop application identity.** It may not present Epicenter's verified consent screen. Google's consent screen names the application receiving the grant, so shipping someone else's identity misrepresents who the user is trusting.
3. **The official build keeps a machine-wide bring-your-own override**, for organizations and advanced users who want their own Google identity and their own quota.
4. **The override is machine-wide, and changing it requires reconnecting every Gmail account on that machine.** Google binds a refresh token to the client that minted it. A stored grant is never reinterpreted under a new client identity: the mismatch fails loudly and asks for a reconnect.
5. **No Epicenter server participates in the Gmail path.** Authorization, code exchange, refresh, every Gmail API call, the access and refresh tokens, and the SQLite mirror are all device-local. Epicenter Cloud and a self-hosted Epicenter instance never broker the flow and never receive Gmail tokens, mail, or metadata. A cloud token broker is refused here, not left open as an implementation detail for a later convenience patch to introduce.
6. **A Desktop client id, and any client secret Google requires alongside it, are public application configuration, not user secrets.** They identify a build, not a person, machine, or install. User secrets are the access and refresh tokens, which clause 5 keeps on the device.

**What is not true yet, stated plainly:** no official Epicenter Google client is provisioned or verified. That is a release task, not an open question in this record: the distribution-owned code path is built, and this record is accepted on that basis. The distribution-owned code path exists, but source builds and current unsigned local bundles are bring-your-own unless built with a test client. No code, UI string, README, or marketing copy may claim a one-click Gmail connect until the official client exists and has passed Google verification. Clause 1 is the committed destination, not a description of current release behavior.

## Consequences

- **`gmail.modify` stays the single scope, and it is restricted.** Verified against Google's Gmail scope table (2026-07-29): `gmail.modify` is a restricted scope. It is also the narrowest single scope that supports both a full local read mirror and label triage; `gmail.readonly` cannot write labels, and adding `gmail.send` would widen the grant for a capability Local Mail deliberately does not ship (ADR-0116).
- **The device-only boundary is what keeps Local Mail out of an annual third-party security assessment.** Google requires a security assessment, renewed at least every 12 months after the assessor's Letter of Assessment, for every app that requests restricted data *and can access that data from or through a third-party server* (verified 2026-07-29). Restricted-scope verification is owed regardless. Clause 5 is therefore load-bearing compliance, not just taste: a cloud token broker would pull Epicenter into a recurring assessment regime for a feature that needs no server at all.
- **Quota is dominated by first imports, not by polling.** `history.list` costs 2 units and `messages.get` costs 20, against a daily free threshold of 80,000,000 units per project (verified 2026-07-29). Steady-state polling is negligible; initial full-mailbox imports across many users are what would consume a shared official project. Clause 3's override is the escape hatch for a heavy mailbox or an organization that would rather spend its own quota, and is the reason clause 3 is not optional convenience.
- **The client secret question stays empirically open.** Google states installed apps "cannot keep secrets" and lists `client_secret` as *Optional* in the installed-app token exchange, and PKCE as recommended. Whether a Google **Desktop** client actually completes code exchange and refresh with no secret is unproven here: the current code posts one. Prefer PKCE without a secret only after a real Desktop-client test proves Google accepts it. If Google requires the field, bundling it in the distribution is public configuration under clause 6, not a confidentiality claim.
- **Forks pay a real cost, and it is Google's, not Epicenter's.** A fork must register its own Google project and, for restricted scopes, complete its own verification before ordinary users can connect. That follows from Google binding consent to a reviewed app identity.
- **Cross-device consent costs one extra sign-in per device, deliberately.** ADR-0082 had left open whether the secret vault (ADR-0074) should sync the refresh token so a second device need not re-consent. It should not, and that question is now closed: ADR-0081 makes a per-device grant free under Google's concurrency ceiling, so re-consenting on a second device is cheap while syncing a Gmail refresh token would put mail credentials on a server and re-trigger the assessment above.
- **What this forecloses:** brokering Gmail OAuth through Epicenter Cloud to spare a distribution from registering its own Google application, and any per-instance Gmail identity that varies with the selected Epicenter server.

## Considered alternatives

- **Hosted vs self-host picks the Client ID (ADR-0082's original shape).** Rejected: the wrong axis. It conflates where Epicenter data lives with who Google issued the app identity to, and it would punish a user of the official signed app for self-hosting their Epicenter instance by demanding Google credentials that nothing technical requires.
- **Everyone brings their own client forever (today's behavior, made permanent).** Rejected: requiring an ordinary user to create a Google Cloud project to read their own mail is not a product. It is the current state, not the destination.
- **Epicenter Cloud brokers the flow and holds the refresh tokens.** Rejected: it puts mail credentials on a server, triggers the recurring restricted-scope security assessment, and contradicts ADR-0068. It is the most tempting shortcut, which is why clause 5 refuses it explicitly rather than leaving it unmentioned.
- **Forks and rebrands reuse Epicenter's verified client.** Rejected: the consent screen is the user's only signal about who receives the grant. A rebrand wearing Epicenter's verified identity makes that signal false, and would put Epicenter's verification at risk for code it did not ship.
- **Self-host operators must register their own Google client (ADR-0082's rejected alternative, inverted).** The original rejected reusing Epicenter's client on sovereignty grounds. That reasoning does not apply: sovereignty from Epicenter's *infrastructure* is real and clause 5 already grants it completely, because no Epicenter infrastructure is in the Gmail path. Forcing a Google project on a self-hoster buys no additional independence from Epicenter, only friction with Google.
